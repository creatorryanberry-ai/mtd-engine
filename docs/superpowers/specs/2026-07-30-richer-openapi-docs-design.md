# Richer OpenAPI / Scalar API docs

## Goal

Make the Scalar docs at `/docs` (and the committed OpenAPI snapshot) complete and explanatory enough for an internal engineer to authenticate the way the app does and exercise the full api-service surface with any HTTP client (Scalar Try it, curl, Postman, Insomnia, etc.).

Postman is a use case, not a deliverable. No checked-in Postman collection.

## Audience

Internal Curator engineers. Write for someone who has not read the app source.

## Current state

- Spec is generated by `scripts/docs/gen-openapi.ts` from `registerRoute` entries loaded via `src/api/openapiManifest.ts`.
- Committed snapshot: `src/api/openapi-v1.json`.
- Scalar (`api-docs/`) embeds that snapshot; staging serves it at `/docs` when `ENABLE_API_DOCS=1`.
- Today the snapshot is thin: ~9 `/api/v1/*` operations, one-line `info.description`, summaries only (no operation descriptions), no `servers`, no `securitySchemes`, no tag descriptions, no examples, schemas mostly bare property names.
- The api service actually serves far more routes (see `src/server/routeManifest.generated.ts`): auth, Plaid, HMRC, transactions, submissions, mileage, categorisation, files, stats, health, plus v1 routes missing from OpenAPI (`events`, `business-settings`).
- Auth is Better Auth under `/api/auth/*` (catch-all). Real clients use session cookies (web) or `Authorization: Bearer <session token>` (native via the bearer plugin). Protected v1 routes use `requireApiAuth`; many legacy routes use `requireAuth` / `ensureAuth` with the same underlying session resolution.

## Approach

Enrich the **generated** OpenAPI (single source of truth). Do not maintain a hand-written overlay or Scalar-only prose that importers never see.

Where the API is incomplete for documentation (missing auth ops in the manifest, untyped request/response bodies, undocumented live routes), change the code and registry so the documented surface matches what the api service serves.

## Scope

### In scope

- Full api-service route coverage from `routeManifest.generated.ts`, excluding web-only routes not on the api service (notably `/api/og`).
- Auth documented as first-class operations (not only a prose note): at least sign-in, sign-up, sign-out, get-session, and `POST /api/auth/validateToken`, plus overview text for cookie vs Bearer.
- Richer `info.description` (what the API is, v1 vs non-v1, how to authenticate, how to try calls).
- `servers` for local and staging (production noted; docs hosting is staging-focused).
- `components.securitySchemes` for bearer + cookie; per-operation `security` (or explicit public).
- Tag descriptions and per-operation descriptions.
- Request/response examples that match real shapes.
- Common error responses (`401`, and `400`/`404` where handlers clearly return them).
- Field-level clarity where schemas are currently bare (Valibot descriptions or equivalent metadata).
- Generator upgrades to emit the above; regenerate committed `src/api/openapi-v1.json`.
- Small handler/schema refactors needed so JSON bodies have real Valibot (or shared) schemas instead of inventing parallel fake types.

### Out of scope

- Checked-in Postman collection or Postman-specific tooling.
- New auth mechanisms or test-only API tokens.
- Exhaustive listing of every Better Auth plugin subpath under `/api/auth/*` (document the ops testers need; note that other paths exist on the catch-all).
- Renaming `openapi-v1.json` (keep filename to avoid churn; title/description clarify it is the full Curator MTD API surface).
- Changing Cloudflare Access on `/docs*` (docs UI gate ≠ API auth).

## Architecture

### Registration

Keep `registerRoute` + generator as the pipeline. Split the OpenAPI manifest by domain for maintainability, e.g.:

- `src/api/openapi/auth.ts`
- `src/api/openapi/v1.ts`
- `src/api/openapi/plaid.ts`
- `src/api/openapi/hmrc.ts`
- `src/api/openapi/transactions.ts`
- `src/api/openapi/submissions.ts`
- …other domains as needed

A single entry (replacing or wrapping today’s `openapiManifest.ts`) imports all domains so `gen-openapi.ts` still has one load path.

### RouteSpec extensions

Extend as needed (names indicative):

- `description?: string` (already exists; use it)
- `security` / `public` so the generator can emit operation-level security
- optional `examples` for request and success response
- optional extra `responses` beyond the default `200`
- keep `input` / `output` as Valibot schemas for JSON APIs

### Generator (`scripts/docs/gen-openapi.ts`)

Emit OpenAPI 3.1 with:

- markdown `info.description`
- `servers`
- top-level `tags` with descriptions
- `components.securitySchemes` (`bearerAuth` HTTP bearer; `cookieAuth` apiKey cookie for the Better Auth session cookie)
- paths with parameters, request bodies, responses, examples
- omit empty optional fields

Auth catch-all routes are registered as explicit path operations in the auth manifest (schemas aligned with Better Auth shapes used by the app and integration tests), not reverse-engineered from every plugin.

### v1 vs non-v1

Both are live on the api host. `info.description` states:

- `/api/v1/*` is the versioned contract tracked by handshake / `API_CONTRACT_VERSION`.
- Older `/api/*` paths are the current product surface and are documented because testers need them.
- Filename `openapi-v1.json` remains historical; the document is the full api-service surface.

### CI / contract guard

- The committed snapshot remains the source of truth: `bun run docs:openapi` must be re-run and committed when the registry changes (same workflow as today).
- A planned breaking-change OpenAPI guard (`openapiDiff` / `scripts/check/openapi.ts`) is not shipped yet; this work does not depend on it.
- Include a lightweight check that every `routeManifest` pattern has a corresponding OpenAPI path (or an explicit allowlisted exception), so coverage cannot silently regress. Catch-all `/api/auth/*` is satisfied by the documented auth operations plus that allowlist note.

## Auth story (must mirror the app)

1. Sign in with `POST /api/auth/sign-in/email` and `{ email, password }` (sign-up when public auth allows, matching demo/test flows).
2. For subsequent calls:
   - **Bearer** (native-style): `Authorization: Bearer <session token>` from the sign-in/session payload — preferred for Scalar Try it, Postman, and curl.
   - **Cookie** (web-style): Better Auth session cookie when the client stores and forwards cookies.
3. `GET /api/auth/get-session` to inspect the session.
4. `POST /api/auth/sign-out` to clear it.
5. Note that staging `/docs` Cloudflare Access is separate from API session auth.

## Quality bar

A route is “done” when:

- It appears in the generated spec with accurate method and path.
- It has a human summary and a short description (what / when / auth / gotchas).
- Auth requirement is correct in OpenAPI security metadata.
- JSON request/response schemas reflect real payloads (refactor handlers to share schemas when today’s code is untyped soup).
- At least one realistic success example where the body is non-trivial.
- Common errors are listed when the handler clearly returns them.

Special cases:

- Multipart / binary (file upload, receipt): document method, auth, content types, and main fields even if OpenAPI multipart support is limited.
- Better Auth: document tester-critical ops; do not claim the list is every possible Better Auth route.

## Delivery shape

Large surface area. Implementation may land as sequenced commits/PRs (generator + auth + overview → finish v1 gaps → domain batches) as long as the end state is full api-service coverage. Prefer not to stop at “v1 only polished.”

## Verification

- `bun run docs:openapi` regenerates `src/api/openapi-v1.json` with no unintended drift.
- Manifest↔OpenAPI coverage check passes.
- Spot-check Scalar locally and/or staging: overview readable, auth ops present, a protected route callable with Bearer after sign-in.

## Non-goals / explicit exclusions

- `/api/og` and any other web-only routes excluded from the api route manifest.
- Product redesign of legacy vs v1 APIs (document both; do not merge or delete routes in this work unless required for accurate schemas).
